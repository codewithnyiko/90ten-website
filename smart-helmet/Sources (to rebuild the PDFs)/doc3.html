What an SDK and an API are and why we ask

API

A list of the messages a system understands and the answer it gives to each. Think of a church office window: you hand in a form filled in the right way and you get an answer back. If the form is wrong, nothing happens. For the helmet, the API is the list of messages it sends (where it is, an alarm) and the messages it accepts (take a photo, join this Wi-Fi).

SDK

A toolkit that comes with the API: ready-made code, examples and a way to test. Without it we write everything from scratch and find the mistakes ourselves. With it, we start faster and make fewer errors.

How online documentation helps us

When the supplier changes something, the online page changes the same day and we see it. With a PDF we only learn about a change if someone remembers to send it. The supplier may serve many clients and may not tell us.

What we really want

We do not want to depend on the supplier's own platform or their way of doing things. We want to talk directly with the helmet: the helmet connects to our server in South Africa, sends us its messages and we send it commands.

The Interface Document we have describes the helmet's side of this, but it was written for the supplier's own server. We need to know whether the same messages work with our server and whether anything still depends on theirs. Their ready-made API may be built around their platform and that may not be what we want.

What we will ask them to confirm

aThe messages between the helmet and a server are the same, whoever runs the server.
bThe helmet does not need the supplier's platform or accounts for anything to work.
cWe get the full list of messages, with examples, in an online place that shows its version and date.
