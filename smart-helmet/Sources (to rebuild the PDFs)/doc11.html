Smart Helmet: Version 1 Plan and Wireframes

We replace the supplier screens now and still use their servers for the data until we get feedback. The way we get the data stays easy to change.

Prepared for Thella Group Services and Imperium Corporate Prepared by 90Ten Group 20 October 2026 Version 1

Where we are today

The helmet reports to the supplier's servers in China and their control room screens show it. Those screens are old and hard to use. We replace the screens now. For the data we still call the supplier's servers until we get feedback on the way forward.

The question we must ask first

Does the supplier platform have an API to read the helmets' positions and alarms and history? Can we have the documentation and a test account? Are we allowed to build our own screens on it?

One rule: easy to change

The screens never talk to the supplier directly. They only talk to our own data layer. Only the connector knows where the data comes from. Moving to our own server later means changing one part and not the screens.

How our system works in version 1

The helmet keeps reporting as it does today. The connector reads from the supplier platform. Later we swap it for the connector to our own server.

Screen 1: Overview

The first thing the control room sees. It answers: is everyone fine and what needs attention?

  1. Four numbers at the top. A glance shows if anything is wrong.
  2. The map of the site. Each filled circle is a helmet and a ring is an alarm. Positions come from the helmet GPS so this works above ground only.
  3. The alarms list. The newest alarm is at the top. Tapping one opens screen 3.

Screen 2: One worker

Pick a worker to see where they have been today from the helmet GPS.

  1. A list of workers with a search box. A filled dot means the helmet is online. An empty dot means it has not been seen.
  2. Where the worker has been today with the time. The last line is where they were last seen.
  3. The black tag marks the last time the helmet reported.
  4. The same route drawn on the map. The map depends on question 3 because the helmet may report positions in a Chinese map system.

Screen 3: Alarm and last seen

What opens when an alarm comes in. It is also how the control room finds out where someone was last seen.

  1. The alarm bar. Who it is and where they were last seen. Two buttons: acknowledge or open the trail.
  2. The last seen card. The place and the time and the battery. If a worker stops moving it says for how long.
  3. Who is close to the worker by GPS. They can be called first. The dashed box shows what comes in the next version once the beacons are confirmed.
  4. The way the worker came on the map. The search finds anyone by name.

Screen 4: Setup and Bluetooth test

Where we check which beacons the helmet can hear and where helmets report. This is how we find out what works before we build the underground part.

  1. Tabs for helmets and the Bluetooth test and the server. The server tab shows the address the helmets report to, which is our own. The beacons tab is for the next version.
  2. Every Bluetooth device the helmets hear with its signal strength. The helmet report lists all of them.
  3. How we use it. We put a real beacon next to a helmet and see if it shows up. That tells us which beacons work.
What version 1 depends on

Access to the supplier platform data and its documentation. Question 3 on the map. The underground trail in the next version also depends on question 4 on beacons and the Bluetooth test on screen 4 can answer it. Everything else in this document can be built from the Interface Document.
